# Custom Instructions

## Google Maps Integration Directive
When working with Google Maps Platform features (such as location-aware journaling, maps, routing, or places), you MUST adhere to the following directives:
1. **Always read the `google-maps-platform` skill (`/skills/system_skills/google_maps_platform/SKILL.md`)** before designing or writing any Maps-related code.
2. **Secure Credentials**: Never hardcode Google Maps API keys. Keys MUST be retrieved securely using environment variables (`import.meta.env.VITE_GOOGLE_MAPS_API_KEY` for client-side React code, or `process.env.GOOGLE_MAPS_API_KEY` for server-side Express code). 
3. **Demo Key**: If the user hasn't provided a key, instruct them on how to generate a Maps Demo Key as per the skill instructions.
4. **Modern APIs Only**: Rely solely on modern APIs (e.g., `@vis.gl/react-google-maps`, `AdvancedMarkerElement`, Places API (New)). Do not use deprecated APIs like `google.maps.Marker` or `google.maps.places.Autocomplete`.
5. **Usage Attribution**: Ensure proper attribution `gmp_mcp_codeassist_v1_aistudio` is applied to Map components.

## Admin Roles Directive
When implementing Role-Based Access Control (RBAC) or generating security checks for elevated admin permissions, you MUST adhere to the following directives:
1. **Never Trust Client Claims**: Rely on a trusted server-side document (e.g., an `admins` collection) to verify admin status.
2. **Firestore Security Rules**: Write an `isAdmin()` helper function in `firestore.rules` that verifies the admin status using `exists(/databases/$(database)/documents/admins/$(request.auth.uid))`.
3. **Prevent Self-Assigned Roles**: During user profile registration, explicitly forbid users from setting their own privileges.
4. **UI Protection**: Hide admin features in the frontend based on the user's role fetched from Firestore, but always enforce security boundaries at the database level with strict rules.

## Notification API Directive
When integrating external notifications (e.g., Slack, Discord, Email) to alert users based on parsed content or system events, you MUST adhere to the following directives:
1. **No Hardcoded Credentials**: Webhook URLs and API keys MUST NOT be hardcoded. Retrieve them securely via environment variables (e.g., `process.env.SLACK_WEBHOOK_URL`, `process.env.DISCORD_WEBHOOK_URL`).
2. **Asynchronous Dispatch**: Notification logic must execute asynchronously in a non-blocking manner (e.g., wrapping in a fire-and-forget `try/catch`). Never fail a primary user operation due to a downstream notification delivery failure.
3. **Structured Triggering**: Rely on a deterministic schema flag (e.g., an `isUrgent` or `notifyAlert` boolean generated by structured LLM output) to trigger notifications, rather than brittle substring matching.
4. **Payload Sanitization**: Ensure that sensitive Personally Identifiable Information (PII) is obfuscated or omitted from webhook payloads, especially when dispatching to shared channels. Use standard payload schemas matching the target service (e.g., `{ content: "..." }` for Discord).

## Gemini API & AI Integration Directive
When integrating AI features using the `@google/genai` SDK for text, chat, structured data, or TTS, you MUST adhere to the following directives:
1. **Model Fallback & Resilience**: Never hardcode a single model string without a fallback. Wrap generation calls in a fallback ladder (e.g., `gemini-3.8-flash`, `gemini-3.1-flash-lite`) and intercept HTTP 503/429 errors to gracefully cascade down the ladder.
2. **Schema Reliability & Parsing**: When requesting JSON structured output, always provide a fallback parsing `try/catch` block. Never assume the returned text is perfectly formatted JSON.
3. **API Key Security**: Always access the API key via `process.env.GEMINI_API_KEY` in server-side context only. The key must NEVER be leaked to the client browser.
4. **Graceful Degradation (TTS/Media)**: For secondary modalities like Text-to-Speech (TTS), wrap the API call in an independent `try/catch` block so that a failure in audio generation does not block the delivery of the primary text response.

## Firebase & Firestore Integration Directive
When implementing database persistence or user authentication, you MUST adhere to the following directives:
1. **Strict Undefined-Stripping**: Sanitize all payloads before passing them to Firestore (`setDoc`, `addDoc`, `updateDoc`). Ensure no `undefined` values are written to the database, as this causes SDK crashes.
2. **Owner-Bound Security**: All user data collections must be secured in `firestore.rules` validating that `request.auth.uid == userId` to prevent unauthorized cross-tenant data access.
3. **Transaction Verification**: Ensure UI state is only updated or cleared *after* a confirmed successful database write. Never fail silently if a save operation is rejected.
4. **Client-Side Auth Flow**: All Google/Firebase authentication (e.g., popup sign-ins) MUST occur on the client side. Tokens can be passed to the backend via headers if server verification is necessary.

## Server-Side Payload & API Directive
When building Express/Vite full-stack APIs, you MUST adhere to the following directives:
1. **Defensive Ingestion**: Never assume `req.body` contains the expected properties. Sanitize and provide fallback defaults (e.g., `const data = req.body || {}`) before destructuring.
2. **Middleware Ordering**: Always mount body-parser middleware (`express.json()`) BEFORE defining endpoint routes.
3. **Consistent Error Bubbling**: Always wrap route handlers in `try/catch` blocks and return appropriate 400/500 HTTP status codes with clean JSON error messages rather than unhandled server crashes.
